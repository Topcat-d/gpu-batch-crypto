# P-256 engine, ABI and public tables

The native library provides three fixed-base implementations for deterministic P-256 ECDSA signing and public-key generation. They share the extracted scalar field, point, RFC 6979 and signature arithmetic. The table-backed paths are working code reached through the public ABI.

| Backend | C selector | Public points | Device table bytes | Multiplication strategy |
|---|---|---:|---:|---|
| `reference` (default) | `BC_P256_REFERENCE` | 0 | 0 | Scalar double-and-add |
| `comb_w8` | `BC_P256_COMB_W8` | 255 | 16,320 | Unsigned 8-bit fixed window; 256 doublings and up to 32 additions |
| `full_window_w8` | `BC_P256_FULL_WINDOW_W8` | 4,224 | 270,336 | Signed 8-bit digits over 33 precomputed windows; up to 33 additions, no scalar-loop doublings |

The legacy name “comb” is retained for discoverability. Its 255-point layout is an ordinary fixed-window table of `[1]G` through `[255]G`, rather than a transposed mathematical comb. The full-window table contains `[d × 2^(8w)]G`, with `w = 0…32` and `d = 1…128`. Signed digits use point negation. Window 32 handles the final carry at `2^256`; omitting it would break high-valued scalars.

## Follow the implementation

1. [C ABI](../src/abi/batchcrypto_abi.cpp) owns opaque contexts, locks, key slots, epochs and reporting.
2. [Execution engine](../src/engine/crypto_engine.cu) validates and packs batches and dispatches CUDA work.
3. [Device runtime](../src/engine/runtime.hpp) owns the stream, reusable work buffers and resident tables.
4. [CUDA kernels](../src/kernels/crypto_kernels.cuh) invoke the [fixed-base implementation](../src/p256/fixed_base.cuh) and [attributed P-256 arithmetic](../src/imported/p256_persistent/p256_persistent.cuh).
5. [Table embedding](../cmake/EmbedP256Tables.cmake) checks binary fingerprints at configure time and compiles public constants through [tables.cpp](../src/p256/tables.cpp).

The source filename `p256_persistent.cuh` records the arithmetic's origin. This library uses bounded synchronous launches and does not include that earlier engine's persistent queue or scheduler. The generic runtime and ABI are independently scoped public implementations around selected arithmetic and table-generation code; this is not a copy of the entire private engine.

## Select through the API

```python
from batchcrypto import Runtime, generate_p256_key

with Runtime("build/Release/batchcrypto.dll", p256_backend="full_window_w8") as engine:
    engine.load_key(0, generate_p256_key(), kind="p256")
    digests = engine.sha256([b"record one", b"record two"])
    signatures = engine.sign(0, digests)
    public_key, epoch = engine.public_key(0)
    assert engine.p256_backend == "full_window_w8"
```

In C, call `bc_set_p256_backend(ctx, BC_P256_FULL_WINDOW_W8)` and check the return status. `bc_get_p256_backend` returns the selected mode. The [C consumer](../examples/c_api.c) exercises all three modes. The [public header](../include/batchcrypto.h) defines the interface.

Selection serializes with that context's other calls and preserves its keys and epochs. The first selection uploads the compiled public table; later selections reuse it. A failed selection returns an error. A context that has selected both table modes retains both allocations until destruction, with their 286,656 combined bytes included in `reserved_device_bytes`. Public tables contain no keys or nonce material and are not cleared after each call. Secret work buffers still follow the runtime's clearing policy.

These additive functions retain C ABI version 1. Python package v0.2 requires the v0.2 native library; an older DLL lacks the new symbols. Existing C callers can continue to use the reference path. Stateless convenience calls also use the reference path; select a table mode through an owned runtime.

## Inspect or regenerate the data

The [data directory](../data/p256) contains both binaries, JSON layouts and SHA-256 fingerprints. Each file begins with a 32-byte header: ASCII `GBCTBL01`, followed by six little-endian 32-bit integers: type, format version, windows, digits per window, entry bytes and reserved zero. Type 1 is `comb_w8`; type 2 is `full_window_w8`.

Each point is 64 bytes: eight little-endian 32-bit limbs of X, then eight of Y, both in the Montgomery domain `coordinate × 2^256 mod p`. The point index is `window × digits + digit − 1`. Including headers, the files are 16,352 and 270,368 bytes. The full-window point payload matches the selected original table; the header is the generic public format.

```sh
python -m pip install .
python tools/generate_p256_tables.py --check
```

Omit `--check` to regenerate the files. The [generator](../tools/generate_p256_tables.py) uses the [attributed affine math helper](../tools/imported/p256_table_math.py) and independently verifies every point with cryptography/OpenSSL public-key derivation. CI regenerates all 4,479 points and compares the binary, metadata and fingerprint bytes. The native build uses checked-in constants and does not need Python or OpenSSL.

## Correctness and performance evidence

The [public backend results](P256_RESULTS.md) publish two complete runs per GPU, charts, per-card batch tradeoffs, latency, and the observed large-batch variability. Full-window batch 256 recorded 224,742–229,039 signatures/s on RTX 4070 Ti and 177,810–194,276/s on RTX 3060.

[Table-backend tests](../tests/test_p256_tables.py) compare all implementations with deterministic OpenSSL signatures, including RFC 6979 input, high scalars, carry boundaries, digest reduction, multiple keys, random inputs and maximum-size batches. Public-key tests cover each byte window and signed-digit boundaries. All 17 library tests passed independently on RTX 4070 Ti and RTX 3060. See [validation](VALIDATION.md) for the scope.

The [backend benchmark](../benchmarks/run_p256_backends.py) compares the CPU, reference, comb and full-window paths using the same keys and digests within a run. It samples batches 1, 8, 64, 256, 1,024 and 4,096, rotates execution order, checks every returned signature and records seven timed calls per cell. Tables and keys are loaded before warmup; timing includes synchronous Python packing, copies, GPU execution, output construction and buffer clearing. Batch formation, queueing, table import and oracle checks are excluded.

```sh
python benchmarks/run_p256_backends.py --library build/Release/batchcrypto.dll --build-dir build --device 0 --iterations 7 --output benchmarks/p256_results/device0.json
```

Commit the source before measuring. The JSON records the source commit and hashes, binary hash, compiler, GPU, CPU, library versions, raw samples and completion accounting. Prior [v0.1 measurements](RESULTS.md) and [historical full-window engine results](HISTORICAL_BENCHMARKS.md) describe different execution paths; their rates do not transfer to these backends.

All three GPU implementations have secret-dependent behavior. Table lookup addresses depend on private scalars or deterministic signing nonces. Public point data does not make those accesses constant time. Correctness and throughput measurements do not establish side-channel resistance; see [security scope](../SECURITY.md).
